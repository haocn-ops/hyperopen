# Stop one thin-history asset from collapsing the whole optimizer universe (calendar poisoning)

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. Maintain this document in accordance with `/hyperopen/.agents/PLANS.md`.

## Purpose / Big Picture

On 2026-07-08 the owner's live `/portfolio/optimize` session showed BTC and ETH — the two assets with the deepest, cleanest native history in the whole universe (1,094 daily points each, quality `passed`) — badged "THIN HISTORY" with assumption cards reading "Excluded - needs assumption" and "History used: No usable native returns". Live nREPL diagnosis (evidence below) proved every asset in the ~79-asset universe was being excluded by a single degenerate condition: one brand-new listing, `perp:GRAM`, listed 2026-07-02 with only 6 daily candles, had a served history window disjoint from several backend-stale series that end 2026-05-31. The shared-calendar intersection across all members was therefore literally empty, and the `insufficient-common-history` gate responded by excluding every member of the universe with one universe-level warning that names nobody. The UI then blamed exactly the wrong assets.

After this change: an asset whose served history cannot overlap the rest of the universe is excluded individually, with a per-instrument warning that names it, while every other asset aligns normally; the readiness "needs an assumption" gate counts each asset's own served history (so a 6-observation newcomer is flagged as needing an assumption even when alignment degrades); and full-history assets can no longer be labeled "thin history" or "no usable native returns" while their bundle series is demonstrably full.

## Context and Orientation

The optimizer loads a per-wallet "history bundle" from the backend history API (api-v2) into app state at `[:portfolio :optimizer :history-data :api-v2-history]`. The bundle carries, per instrument, a served price series (`:series-by-instrument`, each with `:points` rows of `{:time-ms :close :return …}`), plus backend-computed shared calendars (`:common-calendar`, `:return-calendar`) and pre-aligned returns (`:aligned-returns-by-instrument`).

"Alignment" (`src/hyperopen/portfolio/optimizer/application/history_loader/api_v2/alignment.cljs`, entry `align-api-v2-history-inputs`) turns that bundle plus the draft universe into the request's `:history` map: which instruments are eligible, the shared calendar (the sorted vector of `time-ms` values every eligible series has a row for), per-instrument return series re-sampled onto that calendar, and warnings. When the backend calendars are unusable it falls back to a client-side point-level intersection over the eligible members' own series (`calendar/common-calendar` in `history_loader/calendar.cljs` — a plain `set/intersection` of each series' `time-ms` sets).

The failure mechanism, confirmed live:

1. The backend bundle arrived with EMPTY `common-calendar`/`return-calendar` and all-zero-length aligned returns (status `partial`), so the client took the point-level-intersection fallback.
2. `perp:GRAM` (6 points, 2026-07-02→07-07) passed the per-instrument minimum (`default-min-observations` is 2, so `min-return-observations` is 1) and stayed eligible.
3. Nine series (perp:XPL, perp:LINEA, perp:MET, perp:MON, perp:MEGA, perp:PUMP, perp:STBL, perp:WLFI, perp:xyz:CRCL) end 2026-05-31/06-01 — before GRAM's window starts — so the intersection over all members is the empty vector. Removing GRAM alone yields a 138-day calendar (2025-12-15→2026-05-31); measured live with `calendar/common-calendar`.
4. `common-gap?` (`(< (count effective-return-calendar) min-return-observations)`) then set `effective-eligible` to `[]`: every instrument moved to `:excluded-instruments`, with ONE universe-level `{:code :insufficient-common-history :observations 0 :required 1}` warning carrying no instrument-id.
5. Readiness (`setup_readiness.cljs`) computes per-asset native observation counts from the request's `[:history :raw-price-series-by-instrument]` — which alignment populates for ELIGIBLE members only, so it was empty. `short-history-assumption-warnings` therefore saw `max-obs 0 < 360` and stood down: the very gate designed (per its own docstring) to stop a sub-30-observation asset from "poisoning the shared estimation window of every other asset" is disabled exactly when the poisoning is total. Chicken-and-egg.
6. The view models (`view_model/universe.cljs` `native-history-observations`, and the assumption cards/exposure projections) read the same empty post-alignment map, found no observations for anyone, and rendered "Thin history" badges and "No usable native returns" — but only on the excluded assets that carried NO per-instrument warning, i.e. precisely the healthy ones (BTC/ETH were among the 7 instruments the backend did NOT flag stale; the stale ones map to history-status `:stale`, which the badge logic treats as adequate).

Reproduction from a REPL attached to a live session (shadow-cljs nREPL port in `.shadow-cljs/nrepl.port`; evaluate CLJS with `(shadow.cljs.devtools.api/cljs-eval :app "<code>" {})`): read the bundle at the state path above and run `hyperopen.portfolio.optimizer.application.history-loader/align-history-inputs` on `{:universe (:universe draft) :api-v2-history <bundle> …}`; observe `:eligible-instruments []` and `frequencies` of warning codes showing one `:insufficient-common-history`.

Three defects, three fixes (all client-side; the backend data quality issue is reported separately):

- Defect A (readiness counts the wrong series): per-asset observation counts come from the post-alignment eligible-only map, so degraded alignment blinds the assumption gate and the badges. Fix: alignment additionally publishes `:served-observations-by-instrument` — for EVERY universe row, the row count of the instrument's own served series (api series or legacy fallback, whichever alignment chose), computed BEFORE any shared-calendar eligibility decision. Readiness and the universe view-model prefer the aligned raw count when present and fall back to the served count, so an excluded asset still reports its honest depth.
- Defect B (one member nukes everyone): when the shared return calendar falls below the engine minimum, alignment gives up wholesale. Fix: peel — iteratively remove the member whose removal most enlarges the shared return calendar (ties: fewest own finite-return points, then lexicographic id) until the calendar clears `min-return-observations` or one member remains; peeled members become individually excluded with a per-instrument `{:code :insufficient-common-history :instrument-id <id> :observations <its overlap with the survivors' calendar> :required <min>}` warning, and the survivors align normally. If peeling cannot produce a viable calendar the existing total-gap behavior stands.
- Defect C (dishonest copy): with A in place, a full-history asset reports its real count (1,094), so it can never satisfy the "thin history" badge predicate (`< 360`) or the cards' `:short`/`:none` adequacy trigger, and "No usable native returns" (rendered only when observations are nil/zero) becomes unreachable for it. C is verified behavior of A rather than separate code.

`min-return-observations` means: the minimum number of shared return observations the engine needs, `(max 1 (dec min-observations))` where `min-observations` defaults to 2. "Served series" means the per-instrument series the backend bundle carries (or the legacy candle fallback when alignment chose it), independent of whether the instrument survives shared-calendar eligibility.

## Milestones

M1 — Calendar utilities and the peel algorithm (pure, unit-tested). Extend `src/hyperopen/portfolio/optimizer/application/history_loader/calendar.cljs` with the point-level return helpers that today live privately in `api_v2/alignment.cljs` (`point-return-map` → `finite-return-times`/`point-level-return-calendar`/`returns-from-point-level` equivalents) and a new pure `peel-poisoning-members` implementing the Defect-B loop over per-member finite-return time sets (prefix/suffix set-intersection so each round scores every single-member removal in O(n) intersections). The function takes `series-by-id` and `min-return-observations` and returns `nil` (no viable subset, or nothing to peel) or `{:kept-ids #{…} :peeled-ids #{…} :return-calendar [...]}`. Moving the helpers also buys back the line budget `alignment.cljs` needs to stay inside its 540-line namespace-size exception. Acceptance: new unit tests in `test/hyperopen/portfolio/optimizer/application/history_loader_calendar_peel_test.cljs` cover: GRAM-shape (one tiny disjoint member peeled, survivors' calendar restored), two disjoint young members (both peeled even though removing either alone does not improve the empty intersection), nothing-to-peel (calendar already sufficient → nil), and no-viable-subset (all members mutually disjoint → nil).

M2 — Alignment integration. In `api_v2/alignment.cljs`: publish `:served-observations-by-instrument` from the pre-eligibility `rows` (count of `(:points series)` per row, omitting rows with no series); when `common-gap?` fires with more than one eligible member, run the peel; on success mark peeled rows excluded with the per-instrument warning, recompute the eligible set, the effective calendars (client point-level over survivors), and the return series, and clear the gap (the universe-level warning does not fire when peeling succeeds). The legacy path (`history_loader/alignment.cljs`) publishes the same `:served-observations-by-instrument` key (count of each prepared row's normalized history) for dev/fixture parity; peeling stays api-v2-only since production history always arrives through api-v2. Acceptance: new tests in `test/hyperopen/portfolio/optimizer/application/history_loader_api_v2_calendar_poisoning_test.cljs` build a bundle with two long overlapping series + one short disjoint series (backend calendars empty, aligned returns empty, status partial — the live shape) and assert: the long members are eligible with the expected shared calendar; the short member is excluded with an `:insufficient-common-history` warning carrying ITS id; `:served-observations-by-instrument` reports all three honest counts; and a control bundle without the poisoner behaves exactly as before.

M3 — Readiness + view-model sourcing. `setup_readiness.cljs/native-observations-by-id` prefers the aligned raw-series count per instrument and falls back to the served count (so the gate sees GRAM's 6 and BTC's 1,094 even when alignment degrades); `view_model/universe.cljs/native-history-observations` (readiness arity) gains the same served-count fallback after the aligned raw count. ## Surprises & Discoveries

- Observation: the backend bundle was not merely stale — its aligned artifacts were EMPTY while its per-instrument series were full. `:common-calendar []`, `:return-calendar []`, and every one of 81 `aligned-returns-by-instrument` entries zero-length, alongside 1,094-point series for BTC/ETH. The backend evidently hit the same empty-intersection degeneracy and shipped the result without naming a culprit.
  Evidence: live probe of `[:portfolio :optimizer :history-data :api-v2-history]` — `{:return-calendar-count 0, :common-calendar-count 0, :aligned-returns-sample ["perp:XPL" 0], :status :partial, :dataset-version "2026-07-09T00:00:00.000Z"}`.
- Observation: the UI blames exactly the wrong assets, mechanically. Excluded assets WITH backend warnings (`stale-history` etc.) map to per-asset history statuses that read as adequate (`:stale` → adequacy `:ok`); excluded assets WITHOUT any warning — the healthy ones — fall through to "shared gap"/thin-history presentation. The healthier the asset, the more alarming its label.
- Observation: peeling must not require every step to improve the intersection. With TWO young disjoint members, removing either alone leaves the intersection empty (the other still poisons); only after both are peeled does the calendar recover. The loop therefore always peels the argmax candidate (ties: fewest finite-return points, then id) and keeps going until the bar clears or one member remains, rather than stopping at the first non-improving step.
- Observation: upstream trigger for the backend staleness is visible in the bundle itself: Tiingo rejects the backend's proxy-history fetches with HTTP 401 error 10012 "Public API users are limited to querying historical data within the past 365 days" (timestamps 2026-06-21 and 2026-07-01 in the `source-fetch-failed` details for MET/PUMP). Reported to the backend team; no client action.
- Observation (M4 live verify): hot-loading the changed namespaces into the running app via `cljs-eval` also required resetting `setup-readiness/build-request-memo` and `request-builder/align-history-memo` — both memoize on data inputs that had NOT changed, so without the reset the pre-fix alignment kept being served from cache and the fix looked inert.

## Decision Log

- Decision: fix the collapse in the CLIENT even though the trigger was backend data.
  Rationale: the client must be robust to any bundle shape (the backend can degrade again, and a young listing plus one stale series reproduces the geometry without any backend bug); the backend fix is owned by another team and reported separately.
  Date/Author: 2026-07-08 / Claude + owner request.
- Decision: expose pre-eligibility observation counts as a NEW alignment output key (`:served-observations-by-instrument`) instead of widening `:raw-price-series-by-instrument` to include excluded members.
  Rationale: `raw-price-series-by-instrument` feeds expected-return/cadence/risk metadata downstream; widening it would silently admit excluded members into those models. A count-only map changes no engine input and is exactly what the gate and badges need.
  Date/Author: 2026-07-08 / Claude.
- Decision: peel by re-scoring every single-member removal each round (argmax of resulting shared-return-calendar size) rather than simply dropping members below a fixed observation threshold.
  Rationale: a threshold mislabels the failure ("too few points" is not the defect — DISJOINTNESS is: a 282-point series that ends before a 6-point series starts poisons just as hard from the other side), and the argmax loop handles multi-poisoner cases the threshold can't. Cost is bounded: the loop only runs in the degenerate common-gap state, and prefix/suffix intersections keep each round O(n) set intersections.
  Date/Author: 2026-07-08 / Claude.
- Decision: peeled members reuse warning code `:insufficient-common-history` (now with `:instrument-id`) instead of a new code.
  Rationale: it is the same fact ("this asset does not share enough calendar with the rest"), the warning-policy already classifies the code as blocking/insufficient for per-asset status, and readiness already renders it with an honest "shared return observations" message; a new code would need contract, policy, and copy plumbing for zero information gain.
  Date/Author: 2026-07-08 / Claude.
- Decision: keep readiness preferring the ALIGNED raw count over the served count (served is fallback only).
  Rationale: for eligible members the two are equal today, so this is behavior-preserving where things work; the served count only takes over where the aligned map is silent (excluded members), which is exactly the blind spot being fixed.
  Date/Author: 2026-07-08 / Claude.
- Decision: do not implement peeling in the legacy (non-api-v2) alignment path; do add the served-counts key there.
  Rationale: production history always flows through api-v2 (the legacy path exists for dev/fixture sessions and as a per-instrument series fallback INSIDE api-v2 alignment, which the peel already covers); the counts key is added for parity so readiness behaves identically under fixtures.
  Date/Author: 2026-07-08 / Claude.

## Outcomes & Retrospective

(2026-07-08, implementation complete pending owner UI confirmation.) All three client defects fixed and proven: `peel-poisoning-members` restores a 138-day shared calendar on the live-shaped fixture and on the owner's actual session (78/79 eligible, GRAM alone excluded and named); `:served-observations-by-instrument` un-blinds the readiness assumption gate (GRAM flagged `:history-assumption-required` at 6 observations while BTC/ETH report 1,094 and badge `:ok`); the misleading labels are unreachable for full-series assets. Gates 34/34 PASS (6,021 tests). Complexity: modestly increased in `calendar.cljs` (one new algorithm with real justification) and DECREASED at the consumers — readiness and badges now read one honest map instead of inferring depth from an eligibility-filtered artifact. Lesson: any "shared window" computed by intersection needs an explicit story for the member that contributes nothing but takes everything; both the backend and the client lacked one, and the backend still does (reported). Remaining: owner UI confirmation, and the separate backend remediation.

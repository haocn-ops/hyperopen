# Optimizer flow simplification: one-click run, plain-language verdict, honest history assumptions, single workspace

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. This document must be maintained in accordance with `docs/PLANS.md` (and its detailed contract `/.agents/PLANS.md`).

## Purpose / Big Picture

The portfolio optimizer works, but it *feels* like too many steps. A user who just wants "show me a good allocation for what I hold, then let me react to it" must instead: leave an index page, land on an empty universe and search-and-add every asset by hand, read past five numbered setup sections (one of which is falsely labelled "mandatory"), press Run, get navigated to a different page, and then reverse-engineer "what should I do?" from five dense metric cards and a frontier chart. Two of the steps also waste real effort: a "proxy" history-assumption mode asks the user to pick a proxy asset, a relationship strength, and type expected return and volatility — and the optimizer then silently discards all of it and drops the asset from the solve.

After this change a user can: open the optimizer and immediately see their current holdings pre-loaded and an allocation one click away on safe defaults; read a single plain-language sentence that states what the recommended portfolio does to their risk and return before any analyst diagnostics; configure a thin-history asset once, honestly, with no discarded busywork; and see the result appear in place beside their inputs instead of being teleported to a separate page. You will be able to see each of these working in the running app and in tests that fail before the change and pass after.

This plan is scoped to four changes, chosen with the maintainer as the highest end-user-value items from a design audit of the optimizer against *About Face: The Essentials of Interaction Design*. It deliberately excludes six lower-value audit findings (recorded under Context References) and one finding — "show resting orders as open, not filled" — that was already implemented on `main` before this plan was written.

The four changes are sequenced by value-and-risk as four milestones: Milestone 1 (one-click run on safe defaults), Milestone 2 (plain-language verdict on the result), Milestone 3 (remove the proxy history-assumption dead-end), Milestone 4 (collapse the three-page route split into one workspace — Phase 1 only; the harder saved-scenario in-place load is deferred to a separate spike).

## Surprises & Discoveries

Findings already established during research (each shaped a scoping decision):

- Observation: the optimizer already renders results in place on a non-results route. The `/portfolio/optimize/draft` alias renders the recommendation, target-exposure table, and rebalance preview from the retained unsaved run, with no separate page.
  Evidence: `src/hyperopen/portfolio/optimizer/application/view_model/scenario.cljs` `retained-unsaved-route?`/`route-mismatched?`/`scenario-scoped-state`, asserted by `test/hyperopen/views/portfolio/optimize/unsaved_draft_route_test.cljs`. This makes Milestone 4 Phase 1 a small, reversible change rather than a rewrite.

- Observation: the post-run page navigation is a single command, not part of the Run action. `success-commands` in `src/hyperopen/portfolio/optimizer/application/run_bridge_workflow.cljs` emits the navigate only when `new-optimizer-route?` (true on `/optimize/new`); the Run action itself (`actions/run.cljs`) just runs the pipeline. Decoupling the in-place reveal is a change to this one function.

- Observation: the "proxy" history-assumption path is genuinely dead. `application/request_builder.cljs` resolves a proxy implied-correlation but its own docstring says "the engine only consumes conservative entries today"; `application/setup_readiness.cljs` emits `:history-assumption-proxy-not-applied`, a blocking warning that excludes the asset from the solve. So a completed proxy assumption is pure wasted effort.
  Evidence: `domain/history_assumptions.cljs` `engine-backed?` is conservative-only; `setup_readiness` proxy-not-applied message reads "excluded from this optimization".

- Observation: the "Using proxy" status is already shown in muted grey with an explicit warning-styled "excluded" note — it is NOT a false-green badge. So Milestone 3's value is removing wasted modeling effort, not fixing a dishonest indicator. The honest exclusion disclosure must be preserved.

- Observation: the holdings-preseed building block already exists and already degrades gracefully. `actions/universe.cljs` `set-portfolio-optimizer-universe-from-current` filters spot, sorts usable-history-first, and returns no-op when there are no usable exposures. The hard part of Milestone 1 Phase 1b is timing (the account/market snapshot is empty until data loads, so a preseed fired at route entry would see nothing), not the seeding itself.

- Observation: "Horizon: Annualized" in the results provenance strip is a hard-coded literal with zero data binding (`scenario_detail_view.cljs` `provenance-strip`). It can be deleted with no loss of information.

- Observation (Milestone 1 Phase 1b): the natural hook for auto-seed (`load-portfolio-optimizer-route` in `actions/run.cljs`) is unusable because `actions/universe.cljs` already requires `actions/run.cljs` (for `run-portfolio-optimizer-from-draft`, used by the "-and-run" combo actions), so `run.cljs` requiring `universe.cljs` would be a circular dependency. The clean seam is `navigation.cljs` `route-loader-effects`, which already calls every route loader and flows through `split-projection-effects`. The seed returns an `:effects/save-many` projection plus a history-prefetch follow-up, and `projection-effect-ids` (in `navigation.cljs`) already includes `:effects/save-many`, so the split orders them correctly with no extra work.
  Evidence: `actions/universe.cljs` line 3 requires `actions.run`; `navigation.cljs` `projection-effect-ids` = `#{:effects/save :effects/save-many}`; `npm run gates` 33/33 after wiring, including `lint:namespace-boundaries`.

## Context and Orientation

The optimizer is a feature of a ClojureScript single-page trading app rendered with Replicant (a data-driven view library). The reader needs four pieces of vocabulary, each tied to where it lives:

A "view" is a pure function from application state to a data structure describing the DOM; optimizer views live under `src/hyperopen/views/portfolio/optimize/`. Views never perform side effects.

An "action" and an "effect" are how this app changes state and talks to the outside world. The app uses a Nexus-style runtime: a view emits an `:actions/...` keyword with arguments; a pure action handler returns new state plus a list of `:effects/...` to run; effects (HTTP calls, navigation, storage) execute in interpreters under `src/hyperopen/runtime/effect_adapters/`. Adding a brand-new `:actions/...` or `:effects/...` requires a matching contract entry in three places that are checked for exact set-equality by `npm run check`: `src/hyperopen/schema/runtime_registration/portfolio.cljs`, `src/hyperopen/schema/contracts/action_args.cljs`, and `src/hyperopen/portfolio/optimizer/runtime_catalog.cljs`. Reusing an existing action needs none of that.

A "view-model" is a pure function that reads raw state and produces the shaped data a view consumes; optimizer view-models live under `src/hyperopen/portfolio/optimizer/application/view_model/` (notably `workspace.cljs` for the setup surface and `scenario.cljs` for the results surface). Both already read the same shared state paths.

The "draft" is the single live, editable optimizer configuration at state path `[:portfolio :optimizer :draft]`; the most recent solved result is at `[:portfolio :optimizer :last-successful-run]`. These are single, non-scenario-keyed paths: there is exactly one live draft and one last result, and loading a saved scenario `{id}` overwrites these same paths. The three optimizer URLs — `/portfolio/optimize` (an index board of saved scenarios), `/portfolio/optimize/new` (the setup workbench), and `/portfolio/optimize/{id}` (the results page with five tabs) — are selected by a single `case` on the parsed route kind in `src/hyperopen/views/portfolio/optimize/view.cljs`.

The "readiness pill" is the status chip near the Run button (`src/hyperopen/views/portfolio/optimize/setup_actions.cljs` `run-status`) that names why a run is blocked ("Add assets to run", "Loading history", "No usable history", and so on). The Run button stays clickable whenever the universe is non-empty even if a run is not yet possible — clicking acts as a retry — and the honesty lives in the pill, never by silently disabling. This pill must keep working unchanged through all four milestones.

The only required input to run an optimization is at least one asset in the universe: `run-triggerable?` in `application/view_model/workspace.cljs` is `(and (seq (:universe draft)) (not running?))`. Everything else (objective minimum-variance, risk model, return model, and the full constraint set) is pre-filled by `default-draft` in `src/hyperopen/portfolio/optimizer/defaults.cljs`. This fact is the backbone of Milestone 1.

The trading-safety boundary that none of this work may cross: the Execution tab's two-step live-order arming (staged, then "Arm execution", then "Confirm & send"), its "Send N live orders to Hyperliquid? … cannot be undone" copy, the backend-confirmed order lifecycle (never optimistic "Filled"), the read-only/spectate disable, the halt/recovery idempotency guarantees, and the Save-refuses-stale guard. All four milestones operate entirely on pre-trade configuration, the read-only result surface, and navigation; none touches the Execution tab's live-order controls, which remain their own tab-gated section reached via `[:actions/open-portfolio-optimizer-execution]`.

## Plan of Work

### Milestone 1 — One-click run on safe defaults

Goal at the end of the milestone: a user landing on `/portfolio/optimize/new` sees their current holdings already loaded as the universe (when holdings exist), a single prominent "Run on safe defaults" action, and setup sections that read as optional tuning rather than a required five-step sequence — with no false "mandatory" label.

This milestone has two phases. Phase 1a is pure-view and ships first because it carries no data-timing risk. In `src/hyperopen/views/portfolio/optimize/setup_actions.cljs`, change the Run button to read "Run on safe defaults" and confirm it is the single visually-primary action (the `.optimizer-primary-action` styling already exists), keeping "Save draft" demoted and leaving the `run-status` pill (lines ~33-65, ~148-164) untouched. In `src/hyperopen/views/portfolio/optimize/setup_constraint_controls.cljs` (line ~158), replace the trailing literal "mandatory" on section 04 Constraints with an honest, muted "optional" / "defaults applied" token, since no constraint control gates Run. In `src/hyperopen/views/portfolio/optimize/setup_controls.cljs` (the `section-heading`/`disclosure-heading` functions, lines ~40-54) and every caller that passes a number (`setup_universe.cljs` "01", `setup_objective_controls` "02", `setup_model_controls` "03", `setup_constraint_controls` "04", `setup_sections.cljs` "05"), remove or de-emphasize the numeric eyebrow so the sections no longer read as an ordered gauntlet; relabel sections 03/04/05 (already collapsed `<details>` panels) as optional post-run tuning. In `src/hyperopen/views/portfolio/optimize/setup_universe.cljs` (lines ~262-272) make the "Custom | From holdings" strip reflect the actual active source instead of statically pre-highlighting "Custom", and update the "No instruments selected yet" empty state to mention the holdings default. Any new arbitrary Tailwind utilities introduced for these restyles must use static CSS hook classes or the Tailwind safelist, because the dev `--watch` JIT intermittently drops arbitrary classes (a known regression class for this area).

Phase 1b is behavioral: automatically pre-seed the universe from the user's holdings the first time they enter a fresh draft. There is no explicit "new draft" action today (the draft is reset lazily per render when the route id does not match the loaded id), so the cleanest hook is `load-portfolio-optimizer-route` in `src/hyperopen/portfolio/optimizer/actions/run.cljs` (the `:optimize-new` branch). Reuse `set-portfolio-optimizer-universe-from-current` (`actions/universe.cljs`) behind a guard that fires only when the draft universe is empty, the holdings snapshot is loaded with usable exposures, and the draft has not already been seeded — never overwriting a universe the user has since edited or deliberately cleared. Because `current-portfolio-snapshot` (`application/current_portfolio.cljs`) is empty until account and market data load, the seed must re-attempt once that data resolves rather than firing once at route entry and giving up; identify the existing mechanism the codebase already uses for "do X once account data resolves" (see `run_bridge_workflow.cljs` `new-optimizer-route?` and the startup route-refresh path) and reuse it, introducing a one-shot "seed pending" flag if needed. Per the Decision Log, seed the universe only, not the holdings-derived constraints. When holdings are empty or all have unusable history, the existing no-op return leaves the universe empty and the user falls back to manual "Custom" search — which must be communicated, not silent.

### Milestone 2 — Plain-language verdict on the result

Goal at the end of the milestone: the recommendation tab opens with one plain sentence stating what the recommended portfolio does to the user's volatility and expected return and how many trades it implies, framed as estimates with signed deltas, above all analyst diagnostics; the single most likely next step ("Review rebalance") is the one visually-primary action; and the noise field "Horizon: Annualized" is gone.
